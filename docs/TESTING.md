# TESTING — كيف نختبر KotaStore

> الحالة: مقترح. لم يُنفَّذ أي اختبار بعد.

## الطبقتان
| الطبقة | من ينفّذها | أين | متى |
|---|---|---|---|
| **آلية** (وحدات، تكامل، تزامن، E2E) | الوكيل — تعمل في CI تلقائيًا | GitHub Actions | كل PR |
| **يدوية للمالك** (خطوات + نتائج مرجوة) | **أنت** | بيئة `staging` على الإنترنت، من جوالك/حاسوبك | كل مرحلة، قبل الاعتماد للإنتاج |

## بوابة الإصدار
لا ينتقل شيء إلى الإنتاج إلا بـ: **(1)** نجاح كل الفحوص الآلية، **(2)** نجاح سكربت الاختبار اليدوي لتلك الميزة مسجَّلًا في الـ PR (التاريخ + نجح/فشل + لقطات للفاشل).
**أنت لا تحتاج تثبيت شيء على جهازك**: تفتح رابط `staging` وتتبع الخطوات.

## البيئات
- `staging`: نسخة على الإنترنت بقاعدة بيانات **منفصلة** (فرع Neon) و**بيانات وهمية** فقط.
- `production`: متجرك الحقيقي. لا يلمسه أي اختبار.
- الرابط والحسابات التجريبية (مالك، محاسب، أمين مخزن، مندوب) تُنشأ في المرحلة 2 وتُكتب في كل سكربت.

## قالب سكربت الاختبار اليدوي
يُحفظ باسم `docs/manual-tests/phase-N-<موضوع>.md` ويُسلَّم **مع الـ PR** الذي أنتج الميزة.

```
# اختبار يدوي: <الميزة> — المرحلة N
- البيئة: staging  | الجهاز: جوال / حاسوب  | الحساب: <الدور>
- بيانات مسبقة: <ما يجب أن يكون موجودًا>

## الحالة 1: <اسم>
1. افتح <الرابط>.
2. اضغط <زر>.
3. أدخل <قيمة>.
**النتيجة المرجوة:** <ما يجب أن تراه بالضبط>
**النتيجة الفعلية:** ______    ✅ نجح / ❌ فشل    لقطة: ____

## حالة صعبة: <خطأ أو حالة حدّية>
...
```
كل سكربت يحوي **الحالات الصعبة أيضًا** (إدخال خاطئ، كمية غير متاحة، صلاحية ناقصة…)، لا المسار السهل فقط.

## مثال توضيحي (غير نهائي — للمرحلة 7)
**الحالة:** المتغير «مقاس M» متاحه 1.
1. من جوالك افتح المتجر، أضف «مقاس M» للسلة وأتمّ الطلب باسم تجريبي.
2. **المرجو:** رقم طلب وباركود يظهران، والطلب «بانتظار التأكيد».
3. من متصفح آخر (أو نافذة خاصة) حاول شراء نفس المقاس.
4. **المرجو:** المقاس يظهر «غير متوفر» ولا يمكن إضافته.
5. من الإدارة ألغِ الطلب الأول. **المرجو:** المقاس يعود متاحًا فورًا.

## كيف تبلّغ عن فشل
اكتب: رقم الحالة، ما فعلتَه، ما رأيته، لقطة شاشة، الجهاز والمتصفح. وأنا أصلح ثم أعيد السكربت.

## تقليل حمل الاختبار اليدوي (مراجعة 15 نوفمبر)
اختبارك اليدوي عنق زجاجة محتمل. لذلك:
- كل سيناريو E2E يمكن أتمتته يُنفَّذ **آليًا على staging** (Playwright) في كل نشر، وسكربتك اليدوي يركّز على ما لا يُؤتمت: الإحساس بالواجهة على جوالك، الكاميرا والباركود، الطابعة، المطابقة مع أرقامك.
- السكربت اليدوي قصير (≤ 10–15 دقيقة) ويُقسَّم لحالات صغيرة تُنفَّذ على مراحل.
- المال والمخزون يعتمدان على الاختبارات الآلية (خصائص وتزامن) أكثر من اليدوي.

## بيئة الاختبار بلا Docker (v3)
- **أنت:** تجرّب النسخة المنشورة على `staging` فقط (رابط على الإنترنت)، بلا تثبيت.
- **الوكيل:** يطوّر على فرع Neon `dev`؛ التزامن والتكامل يعملان في CI على PostgreSQL تابع لـGitHub (ADR-0031).
- بيانات `staging` تأتي من `pnpm seed` (وهمية)؛ إعادة ضبطها بإعادة التفريع ثم seed.

## اختبارات تكامل المبيعات v5 (ADR-0032) — آلية، أولوية للمال والمخزون
> مقترحة وغير منفَّذة. تُوزَّع على مراحلها (7 و9 و10 و27) وتعمل في كل PR حساس (`full-matrix`).

| الفئة | الاختبار |
|---|---|
| **خصائص (property)** | لأي سلسلة أحداث (حجز، تعديل، صرف، تسليم كامل/جزئي، إعادة محاولة، مرتجع جزئي، رد مبلغ): ميزان المراجعة متوازن · 1200+1210 = قيمة المخزون · 1150 = Σ العُهد غير المؤكَّدة · 1140 = Σ `balance_due` للمُسلَّم · 2150 = Σ العرابين غير المستهلَكة |
| **توازن R4** | لكل توليفة دفع (كاملة/جزئية/مسبقة/بلا دفع) مع خصم وتقريب 3 خانات |
| **الطلب** | `grand_total` يطابق الأسطر والمكوّنات؛ `edit_order` متزامن مع طلب آخر بلا جمود؛ تعديل يتجاوز المتاح يفشل بلا أثر جزئي؛ طلب إداري بزبون `blocked` يُرفض |
| **الإرسال والتسليم** | `dispatch_order` ينقص المخزون ويخزّن التكلفة ولا يتكرر (idempotent)؛ إعادة محاولة بمندوب آخر لا تكرر الخروج؛ تسليم جزئي يعيد غير المسلَّم؛ دفع مسبق كامل لا يُنشئ عُهدة |
| **النقد** | دفعة نقدية تظهر في سطر تسليم واحد فقط؛ تأكيد مزدوج يُرفض؛ المندوب لا يؤكد تسليمه؛ فرق جزئي يُرحَّل بالسياسة |
| **المرتجع** | يعيد المخزون **بتكلفة السطر لا بالمتوسط الحالي**؛ التالف إلى 5020؛ مجموع المرتجع ≤ المسلَّم؛ عكس العمولة بالتناسب؛ رد النقد بصلاحية مدير |
| **الجرد** | خفض `on_hand` دون الحجوزات النشطة يُرفض أو يمرّ بقرار صريح |
| **الترحيل الرجعي** | يشمل طلبات 0α؛ تشغيله مرتين لا يكرر؛ طلب بلا حركة صرف مسجَّلة التكلفة لا يُرحَّل ويظهر في لوحة السلامة |
| **إلغاء بعد عربون** | يبقى 2150 حتى الرد، ويظهر في لوحة السلامة |

### فحوص السلامة اليومية (لوحة «سلامة الحسابات» — مبيعات)
لا طلب مُسلَّم بلا قيد R4/R5 · لا قيد بلا مصدر · `delivered_qty + returned_qty ≤ qty` · لا حجز `active` لطلب منتهٍ/ملغي · عُهد أقدم من الحد · 2150 لا يحوي رصيدًا لطلبات مُسلَّمة · لا دفعة نقدية مؤكَّدة بلا سطر تسليم · `paid_total` = مجموع الدفعات المؤكَّدة · لا طلب مُرسَل بلا حركة صرف بتكلفة.
