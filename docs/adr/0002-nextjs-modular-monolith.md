# ADR-0002: الإطار والمعمارية — Next.js (App Router) + Modular Monolith
الحالة: مقترح

## السياق
نحتاج متجرًا عامًا سريعًا (SEO مهم لإعلانات وبحث)، ولوحة إدارة، وشاشة مندوب، وواجهات Webhook، وفريق صغير.

## الخيارات
1. **Next.js + تطبيق واحد مقسّم لوحدات** — SSR/ISR للمتجر، Server Actions للإدارة، Route Handlers للـ Webhooks؛ معاملات ذرية بين المخزون والمحاسبة؛ نشر واحد.
2. واجهة React منفصلة + خادم API منفصل (NestJS) — فصل أوضح، لكن مشروعان ونشران وتكرار أنواع.
3. Microservices — مبالغ فيه لهذا الحجم، ويكسر الذرّية بين الحجز والقيد.

## القرار المقترح
الخيار 1، مع حدود صارمة بين الوحدات (انظر ARCHITECTURE §3) وطبقة خدمات لا تعتمد على Next.js حتى يمكن فصلها لاحقًا.

## السبب
أبسط طريق لنظام آمن ومتماسك، ويطابق ما تفضّله من تقنيات.

## العواقب والمخاطر
- تغيّر الإطار بين الإصدارات: نثبّت الإصدارات ونراجع الترقيات في PR مستقل.
- خطر تسرّب منطق الأعمال إلى المسارات: يُمنع بمراجعة وقاعدة في AGENTS.md.

## ما لم يُختبر
أداء Server Actions تحت حمل، وتشغيل المهام الخلفية بجانب التطبيق.

## ملحق (15 نوفمبر): قيود التشغيل على الاستضافة المجانية
التطبيق سيعمل على Cloudflare Workers (ADR-0014): لا عملية دائمة، ذاكرة وحجم حزمة وزمن معالج محدودة، وبعض مكتبات Node لا تعمل. **القاعدة:** أي مكتبة جديدة تُفحص توافقها مع Workers قبل اعتمادها. تجربة الجدوى في المرحلة 1 تقرر؛ إن فشلت نعيد النظر معك.

## ملحق (15 نوفمبر، مراجعة)
إن أثبتت تجربة الجدوى (ADR-0014) أن تطبيقًا واحدًا لا يتسع في حدود Workers، يُسمح بتقسيمه **نشريًا** إلى مسارين (متجر / إدارة+POS+مندوب) من نفس المستودع والوحدات، دون تغيير حدود الوحدات ولا قاعدة البيانات.
