# ADR-0003: قاعدة البيانات — PostgreSQL، والـ ORM — Prisma
الحالة: مقترح

## السياق
نحتاج معاملات ACID، أقفال صفوف للحجز، دقة في الأرقام المالية، وقيودًا على مستوى القاعدة (CHECK، UNIQUE).

## الخيارات (قاعدة البيانات)
1. **PostgreSQL** — معاملات قوية، `SELECT … FOR UPDATE`، قيود غنية، JSON، فهارس جزئية.
2. MySQL/MariaDB — مقبول لكنه أضعف في القيود والأنواع.
3. SQLite — لا يناسب التزامن المتعدد والإنتاج هنا.

## الخيارات (ORM)
1. **Prisma** — ترحيلات (migrations) ناضجة، أنواع مولّدة، توثيق واسع. نستخدم SQL خامًا في الأماكن الحرجة (قفل الحجز).
2. Drizzle — أخف وأقرب لـ SQL، لكنه أقل نضجًا في الترحيلات.
3. SQL خام فقط — أقصى تحكم، أكثر عملًا وأخطاء.

## القرار المقترح
PostgreSQL + Prisma. المال أعداد صحيحة (`BigInt`/`Int`) لا `Float`. قيود CHECK وUNIQUE في القاعدة وليس في الكود وحده.

## السبب
نريد أن تكون الصحة مفروضة من القاعدة نفسها (قيد متوازن، مخزون غير سالب، رقم طلب فريد).

## العواقب والمخاطر
- بعض الاستعلامات الحرجة تحتاج SQL خام وتغطية اختبار أعلى.
- Prisma يضيف طبقة: نراقب الأداء.

## ما لم يُختبر
سلوك القفل تحت تزامن عالٍ، وحجم الترحيلات — يُختبران في المراحل 4 و7.

---
## ملحق (15 نوفمبر): الاستضافة المجانية تؤثر على الاختيار
- القاعدة المقترحة: **Neon Postgres** (انظر ADR-0014).
- **ORM غير محسوم:** Prisma مقترح، لكنه على Cloudflare Workers يحتاج محوّل تشغيل (driver adapter) مع تعقيدات حجم الحزمة. **Drizzle** أخف وأنسب لبيئات السيرفرلس. يُحسم بتجربة الجدوى (المرحلة 1) ونسألك قبل الاعتماد.
- **قفل الحجز (مُعدَّل 15 نوفمبر):** لا عمود عدّاد `reserved`؛ بل جدول `reservations` ودالة PostgreSQL `reserve_stock` تُستدعى كعبارة واحدة (انظر الملحق في ADR-0006). السبب: العدّاد لا يتوافق مع الانتهاء الكسول. يُثبَت باختبار تزامن (لم يُختبر).
- **قاعدة عامة للعمليات الحرجة على Workers:** العمليات متعددة الخطوات (طلب + حجز + Outbox، أو قيد محاسبي) تُنفَّذ **كدالة/إجراء PostgreSQL واحد** أو عبر محرك يدعم المعاملات التفاعلية؛ لأن سائق HTTP في Neon لا يناسب المعاملات التفاعلية (يُتحقق في تجربة الجدوى). SQL الخام الحرج يُغطى باختبارات تكامل على PostgreSQL حقيقي.
