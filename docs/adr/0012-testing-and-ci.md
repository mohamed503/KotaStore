# ADR-0012: الاختبار ومصفوفة CI
الحالة: مقترح (محدَّث 15 نوفمبر: طبقتان: آلي + يدوي من المالك)

## القرارات المقترحة
- **أنواع الاختبار**: وحدات (Vitest)، تكامل مع PostgreSQL حقيقي، E2E (Playwright)، اختبارات تزامن للحجز، اختبارات خصائص (property-based) للمحاسبة.
- **المصفوفة**: البناء والفحص (lint + typecheck) والوحدات تعمل على **Ubuntu وWindows وmacOS** مع كل PR.
- **اختبارات قاعدة البيانات**: على Ubuntu مع حاوية خدمة PostgreSQL (حاويات الخدمة غير متاحة على Windows/macOS في GitHub Actions). **لذلك هذا استثناء من «كل الأنظمة»** وهو بحاجة لموافقتك؛ البديل تشغيل PostgreSQL مثبّتًا مباشرة على كل نظام (أبطأ وأعقد).
- **E2E**: Ubuntu أولًا؛ Windows/macOS إن ثبتت الحاجة.
- **فحص أسرار** (gitleaks) في CI: قد يحتاج ترخيصًا إن كان المستودع تحت منظمة.
- **تغطية**: عتبة مبدئية للوحدات المالية 90%+ تُثبَّت في المرحلة 1 (رقم مقترح لم يُحسم).
- **Node**: إصدار LTS مثبَّت في `.nvmrc` ويُراجع عند التنفيذ.
- **حماية الفرع الرئيسي** (إعدادات في GitHub لا ملفات): PR إجباري، فحوص مطلوبة، مراجعة واحدة على الأقل، منع الدفع المباشر. **يضبطها المالك يدويًا**.

## ملاحظة عن ملف الـ workflow الحالي
قبل وجود `package.json` تنجح الوظائف دون تشغيل شيء (خطوات مشروطة). هذا مؤقت حتى المرحلة 1، ولا يُعتبر دليلًا على أي نجاح.

## ما لم يُختبر
ملف الـ workflow نفسه لم يُشغَّل على GitHub بعد.

## ملحق (15 نوفمبر): طبقتان للاختبار
**قرار المالك:** الاختبار «يدوي من قبلي بخطوات تحددها لي ونتائج مرجوة»، ولك أنت (الوكيل) اختباراتك.
1. **آلي (مسؤولية الوكيل):** Vitest وPlaywright واختبارات تزامن ومحاسبة، تعمل في CI.
2. **يدوي (مسؤولية المالك):** سكربت خطوات لكل ميزة في `docs/manual-tests/` بقالب ثابت (انظر `docs/TESTING.md`)، يُنفَّذ على **بيئة اختبار (staging)** بقاعدة بيانات منفصلة وبيانات وهمية، وتُسجَّل النتيجة (نجح/فشل + لقطة).
3. **بوابة الإصدار للإنتاج:** نجاح الآلي + نجاح اليدوي مسجَّلًا في الـ PR.

**تكلفة CI:** مجانية بلا حد إن كان المستودع **عامًا** (مقترح ADR-0013). إن اخترت مستودعًا خاصًا فدقائق macOS تُخصم 10 أضعاف، فنقصر macOS/Windows على الدمج أو التشغيل اليدوي.

**بيئات:** `staging` (فرع Neon منفصل ونشر معاينة) للاختبار اليدوي، و`production`. لا يلمس أي اختبار قاعدة الإنتاج أبدًا.

## ملحق (15 نوفمبر، مراجعة): مستويات CI والمراجعة (يعدّل قرار «كل PR على الأنظمة الثلاثة»)
**السبب:** النشر على Linux (Cloudflare)، ومصفوفة ثلاثية على كل PR تبطئ العمل وتستهلك الدقائق، وتحمي في الغالب من مشاكل مسارات/نهايات أسطر لا من أخطاء الأعمال.
- **كل PR (إلزامي للدمج):** Linux فقط: lint، typecheck، وحدات، بناء، تكامل مع PostgreSQL، فحص أسرار.
- **Windows وmacOS:** تعملان **عند الدمج في الفرع الرئيسي، وليليًا، ويدويًا، وعند وسم PR بـ`full-matrix`**. فشلهما يفتح Issue عاجلًا ولا يُترك.
- **PRs الحساسة** (مال، مخزون، مخطط بيانات، أمان) تُوسَم `full-matrix` وجوبًا.
- إن فضّلتَ الإبقاء على الثلاثة لكل PR فهي مجرد تغيير سطرين في `ci.yml` (عُلِّق عليهما). **قرارك.**
- مراجعة الـPR: **ثقيلة** (مراجع مستقل + موافقة المالك) للمستويات الحساسة فقط؛ **خفيفة** (فحوص آلية + مراجعة سريعة) للواجهة والنصوص. انظر AGENTS §1.

## ملحق (v3): بيئة التطوير
لا Docker ولا قاعدة محلية؛ التطوير على فرع Neon `dev` واختبارات التكامل في CI على حاوية GitHub (ADR-0031).
