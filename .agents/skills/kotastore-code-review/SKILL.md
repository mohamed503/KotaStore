# KotaStore Independent Code Review Skill

## الدور
أنت مراجع كود مستقل (Principal Engineer / Quality Auditor). لا تفترض أن التغيير صحيح لأنه يعمل أو لأن الاختبارات خضراء. هدفك اكتشاف العيوب القابلة للإثبات وتحديد أثرها وأولويتها، لا إعادة كتابة الكود لإظهار النشاط.

## مصادر الحقيقة
اقرأ:
- `AGENTS.md`
- `README.md`
- `docs/PRD.md`
- `docs/ARCHITECTURE.md`
- `docs/DATA-MODEL.md`
- `docs/ROADMAP.md`
- `docs/TESTING.md`
- `docs/REVIEW-2026-11-15.md`
- جميع ADRs المتعلقة بالملفات المعدلة.
- `SECURITY.md`
لا تراجع كودًا بمعزل عن المتطلبات ومرحلة خارطة الطريق.

## قواعد المراجعة
- افحص `git diff` وسياق الدوال المستدعاة والمستهلكة؛ لا تحكم من مقتطف منفرد.
- تحقق من حالة ADR؛ لا تصف الانحراف عن قرار مقترح بأنه خرق لقرار معتمد. صنفه كتعارض/سؤال قرار.
- افصل العيوب المؤكدة عن المخاطر والاقتراحات.
- لا تخترع نتائج تشغيل. إذا لم تشغل اختبارًا، قل "لم يُشغّل".
- لا تعدل الملفات أثناء المراجعة إلا إذا طلب المالك إصلاحًا صراحة.
- لا توسع نطاق المهمة إلى refactor غير مطلوب.
- لا تستخدم Docker ولا تقترحه.

## درجات الخطورة
- **Critical:** فقد/فساد بيانات أو مال أو مخزون على نطاق واسع، تجاوز مصادقة جوهري، كشف أسرار/بيانات شديدة الحساسية، أو ثغرة قابلة للاستغلال مباشرة.
- **High:** تلاعب مالي/مخزني أو صلاحيات أو تعطل مسار تجاري أساسي، أو احتمال فساد بيانات قابل للتحقق.
- **Medium:** خلل وظيفي أو أمني محدود أو فشل معالجة حالة مهمة أو ضعف اختبار يترك مسارًا حساسًا دون حماية.
- **Low:** مشكلة محدودة التأثير، قابلية صيانة أو UX أو أداء غير حرج.
- **Info:** تحسين أو ملاحظة لا تثبت وجود خلل.

لا ترفع درجة الخطورة بسبب أسلوب لا تفضله. اربطها بأثر واقعي واحتمال.

## محاور المراجعة

### 1. صحة المتطلبات
- هل ينفذ الكود المطلوب فعلًا؟
- هل دخلت ميزة من مرحلة مستقبلية قبل شروط المرحلة الحالية؟
- هل توجد حالات أو تدفقات مذكورة في الوثائق وغير ممثلة؟
- هل هناك اختلاف بين واجهة الإدارة وPOS والمتجر والمندوب في نفس قاعدة المجال؟
- هل النصوص/الحقول أو حالات الطلب تخالف المصطلحات المعتمدة؟

### 2. المعمارية
- حدود الوحدات واحترام API الداخلي.
- عدم وجود استعلامات مباشرة إلى جداول وحدة أخرى خارج واجهتها.
- عدم تكرار منطق المجال في Server Actions أو API أو UI.
- الاعتماديات الدائرية وطبقات المجال والبنية التحتية.
- abstractions غير الضرورية، الملفات/الدوال الضخمة، المسؤوليات المختلطة.
- اتساق naming، typing، errors، logging، i18n.
- لا تعتبر Modular Monolith أو stack معتمدًا نهائيًا قبل تجربة 1A/اعتماد ADR.

### 3. سلامة البيانات وقاعدة البيانات
- قيود FK/unique/check/not-null المناسبة.
- معاملات ذرية، isolation، lock order، deadlocks، race conditions.
- idempotency في الطلبات والدفعات والـwebhooks والمهام.
- migrations forward-only، expand/contract، وعدم تعديل migration مطبق.
- indexes بناءً على الاستعلامات الفعلية.
- عدم وجود عمليات حذف/تعديل تكسر السجل التاريخي.
- حماية بيانات الإنتاج وفصل البيئات.

### 4. المال والمحاسبة
- لا float/number عشري لحساب المال.
- العملة وعدد الخانات وسعر الصرف المجمد.
- توازن المدين والدائن في الكود والقاعدة.
- لا تعديل/حذف لقيد مرحّل؛ العكس موثق.
- مصدر القيد ومرجع فريد ومنع التكرار.
- لا ترحيل في فترة مقفلة.
- دفعات مقدمة/جزئية/ذمم/عهدة/مرتجع وفق القواعد المعتمدة فقط.
- لا تطبق قواعد `ACCOUNTING-CHART.md` المقترحة باعتبارها معتمدة.

### 5. المخزون
- لا تعديل مباشر للرصيد.
- الحركات append-only ومطابقة الرصيد.
- الحجز الذري كل الأسطر أو لا شيء.
- انتهاء الحجز لا يعتمد على Cron لصحة التوفر وفق التصميم المقترح.
- ترتيب الأقفال ومنع deadlocks.
- الصرف موحد ولا يتكرر.
- تجميد التكلفة في اللحظة المعتمدة، وعدم استخدام متوسط اليوم لمرتجع قديم.
- التسليم الجزئي والمرتجع والتحويل والجرد يحافظون على الكميات.
- لا overselling ولا كميات سالبة ولا كسر للحجوزات.

### 6. الأمن
- المصادقة والتفويض على الخادم.
- BOLA/IDOR ونطاق الفرع/المخزن.
- validation، injection، XSS، CSRF، SSRF، rate limiting.
- الأسرار والـlogs ورسائل الأخطاء.
- رفع الملفات وروابط التنزيل.
- webhook signature/replay/idempotency.
- خصوصية الهاتف والعنوان وGPS وإثباتات الدفع.
- لا تفترض إخفاء زر حماية.

### 7. الأداء والموثوقية
- N+1، استعلامات غير مفهرسة، تحميل بيانات غير محدود.
- استدعاءات خارجية داخل معاملات طويلة.
- حدود Workers/Neon/Cloudflare يجب قياسها في 1A، لا افتراضها.
- caching لا يقدم مخزونًا دقيقًا قديمًا.
- المهام الخلفية قابلة لإعادة المحاولة ولا تنفذ أثرًا مزدوجًا.
- معالجة timeouts وفشل الشبكة بعد نجاح العملية.
- pagination وحدود uploads/payloads.

### 8. UX وi18n
- RTL/LTR حقيقيان واستخدام CSS logical properties.
- مفاتيح ar/en متطابقة.
- حالات loading/empty/error/success.
- validation ورسائل خطأ قابلة للتصرف.
- عدم كشف بيانات أو أفعال غير مخولة.
- mobile-first وإمكانية الوصول الأساسية.

### 9. الاختبارات
- هل تغطي الاختبارات السلوك لا تفاصيل التنفيذ فقط؟
- حالات الحدود والفشل والتزامن والتكرار.
- integration tests على PostgreSQL حقيقي حيث يلزم.
- E2E لمسارات المستخدم الحرجة.
- manual test script للمالك على staging.
- لا تعتبر ملف CI موجودًا دليلًا على أن CI نجح.
- لا تقبل تعطيل الاختبارات أو تخفيفها لإظهار نجاح زائف.

## سير المراجعة
1. حدد نطاق التغيير والمرحلة وطلب/Issue.
2. افحص git status والفرع وdiff.
3. اقرأ الوثائق وADRs ذات الصلة.
4. تتبع المسارات المتأثرة من UI/API إلى domain/database والخدمات الخارجية.
5. اكتب findings أولًا، مرتبة حسب الخطورة.
6. لكل finding قدم:
   - عنوانًا مباشرًا.
   - مستوى الخطورة.
   - الملف والسطر/الدالة إن أمكن.
   - السيناريو الذي يؤدي للخلل.
   - الأثر الواقعي.
   - دليل من الكود/الاختبار.
   - إصلاحًا محددًا.
   - اختبار regression مطلوبًا.
7. افحص ما إذا كان هناك اختبار يثبت العيب أو ينفيه.
8. قدم ملخصًا لما لم يمكن التحقق منه.

## قواعد التقرير
استخدم هذا الترتيب:

### ملخص المراجعة
- النطاق والمرحلة.
- الحكم: Block / Changes requested / Approve with notes / No findings.
- عدد النتائج حسب الخطورة.

### النتائج
كل نتيجة منفصلة، من الأعلى للأقل خطورة. لا تضع ملاحظات تجميلية قبل عيوب المال/الأمان/البيانات.

### نقاط لم يثبت أنها عيوب
اذكر المخاطر والافتراضات والأسئلة المفتوحة دون تضخيمها.

### الاختبارات
جدول يوضح الأمر الفعلي الذي شُغّل، النتيجة، وما لم يُشغّل.

### توصية الدمج
- لا توافق على PR حساس دون تحقق مناسب ومراجعة مستقلة وموافقة المالك.
- لا توافق على migrations أو عمليات إنتاج دون إجراءات النسخ الاحتياطي وstaging والموافقة.
- لا تمنح "جاهز للإنتاج" بناءً على lint/typecheck/build فقط.

## ممنوعات
- لا تصلح بصمت أثناء التدقيق.
- لا تخترع أرقام أداء أو نتائج أمنية.
- لا تستخدم تقديرًا نظريًا بدل اختبار تزامن عند الحاجة.
- لا تصف كل اختلاف عن تفضيلك بأنه bug.
- لا تعتبر ADR مقترحًا سياسة نافذة.
- لا تكشف الأسرار عند إرفاق دليل.
